# Antídoto web

Sitio de antidotocolombia.com: estudio creativo empresarial colombiano (formaciones vivenciales, producción audiovisual, catering corporativo, diseño de productos). Rediseño multipágina en Astro que reemplaza la SPA de React actual.

## Comandos

- `npm run dev`: servidor de desarrollo en http://localhost:4321
- `npm run build`: genera el sitio estático en `dist/`
- `npm run check`: chequeo de tipos de Astro (requiere TypeScript 6, no 7)
- `npm test`: pruebas del sitio (Vitest, carpeta `tests/`)
- `npm run pixel:posters`: regenera los PNG quietos del estudio y la sala (`src/assets/pixel/`); `tests/pixel.test.ts` falla si quedan viejos
- `npm run verificar`: revisa `dist/` después del build: enlaces internos rotos, un solo `h1` por página, migas en las internas y ninguna ancla de la home en la nav
- API: `cd api && npm run dev | npm test | npm run check` (ver `api/README.md`). El panel y el portal se construyen con `npm run admin:build` (lo corren solos `dev`, `test`, `check` y `deploy`); `npm run admin:watch` los reconstruye mientras corre `wrangler dev`
- `npm run preview`: sirve `dist/`

## Stack

- Astro 7, salida estática (`output: 'static'`, `trailingSlash: 'always'`, formato `directory`).
- Tailwind 4 vía `@tailwindcss/vite`; los tokens de marca están en `@theme` en `src/styles/global.css`. Los componentes usan CSS con alcance local (`<style>` en cada `.astro`) que lee esos tokens.
- Multipágina real: cada página es un documento. El paso entre páginas usa view transitions nativas entre documentos (`@view-transition { navigation: auto }` en `global.css`), sin `ClientRouter` ni router SPA. La nueva página sube como líquido (`clip-path`); la nav y la burbuja de contacto tienen `view-transition-name` propio y quedan quietas; los títulos de servicio comparten nombre para transformarse de una página a otra. Los scripts inicializan una vez al cargar (no hay `astro:page-load`).
- Imágenes con `astro:assets` (WebP y `srcset` en el build). Fotos en `src/assets/fotos/`, logos de clientes en `src/assets/clientes/` (en blanco; el CSS los pasa a tinta con `filter: brightness(0)` sobre fondos claros). La franja de logos de la home usa los originales a color de `src/assets/clientes-color/` (copias de `marca/clientes/`).
- Sin React. El cotizador de `/contacto/` es JS propio: arma el mensaje y abre `wa.me`. Si el build trae `PUBLIC_API_URL`, suma un paso de contacto y, solo con la autorización marcada, envía el lead a la API (`fetch` con `keepalive` y `text/plain`, fail-open: WhatsApp se abre igual). Sin la variable no envía nada a ningún servidor.
- Lógica de negocio en `api/`: Worker de Cloudflare + D1 + Drizzle + R2, paquete aparte con su propio `package.json`. Leads, cron de seguimiento, correos con Resend y email marketing (suscripción con doble confirmación, campañas por lotes, webhook de Resend y baja de un clic). Detalle en `api/README.md`.
- Panel de administración (06/10/2026, reemplaza a la bandeja de JS propio): Preact + Vite en `api/admin/`, construido en `api/dist-admin/` y servido por el Worker en `/admin/` con el binding `ASSETS` y CSP estricta (sin nada en línea). Diseño claro de marca (tokens copiados de `global.css`, Poppins y Cal Sans), barra lateral por grupos, Ctrl+K, carga por pantalla (base ~15 KB gzip). Roles admin, comercial, producción, contenido y solo lectura con matriz de permisos en la API (`api/src/permisos.ts`, rutas por módulo en `api/src/rutas/`), auditoría, ajustes sin desplegar (tope y encendido del chat, regalo de novedades, video del hero), sesiones propias, conversaciones del chat, contenido del sitio, proyectos y organizaciones, sistema y exportaciones a CSV. Portal de proyectos para clientes en `/portal/` (misma app, `portal.html`): enlace mágico y cookie propios, solo su organización y lo marcado como visible, aprobar entregables, pedir cambios y comentar. Migraciones 0005 a 0009. Los textos del panel van solo en español; los del sitio, en los dos idiomas.
- Contenido editable: blog, casos, vacantes, preguntas frecuentes y clientes se publican desde el panel (`api/src/contenido/esquemas.ts`). El build los lee con el cargador `src/lib/cms/` (envuelve los `glob()` y los datos de `src/data/faq.ts` y `clientes.ts`; una entrada del panel reemplaza a la local con la misma clave), que baja las imágenes a `src/content/.cms/` (fuera de git) para que `astro:assets` las optimice. Sin `PUBLIC_API_URL` todo es local; con ella, si la API falla en CI el build se detiene (en local solo avisa; `CMS_ESTRICTO=1` lo fuerza). Los componentes leen preguntas, clientes, vacantes y ajustes con `obtenerPreguntas()`, `obtenerClientes()`, `obtenerVacantes()` y `obtenerAjustes()` de `src/data/contenido.ts`, nunca de `faq.ts` o `clientes.ts` directo. Publicar el sitio desde el panel dispara `preview.yml` o `deploy.yml` con `GITHUB_DISPATCH_TOKEN`.
- PWA: `integraciones/service-worker.mjs` genera `dist/sw.js` desde `src/pwa/sw.js` en cada build (versión por hash del contenido y precache de las páginas offline, sus assets, fuentes e íconos). Páginas con red primero y respaldo en caché o en `/offline/` (`/en/offline/`); `/_astro/` y fuentes con caché primero; imágenes con revalidación. Solo GET del mismo origen: la API y WhatsApp no pasan por el service worker. Se registra en `Base.astro` después de `load` y solo en producción. Íconos `maskable` aparte (`icon-maskable-*.png`) con margen para la zona segura.
- Chat con IA (`src/components/Asesor.astro`, lógica en `src/lib/asesor.ts`; API en `api/src/asesor/`): burbuja doble de WhatsApp e IA (copiada de codebymike.net a pedido del dueño, 03/10/2026) que abre un menú: WhatsApp primero, chat con IA después; en las páginas indexables, solo con `PUBLIC_API_URL`. Sabe lo que publica el sitio (servicios con sus ofertas, soluciones por área, las preguntas de `src/data/faq.ts`, `ui.ts` y clientes, con enlaces a cada página), no da precios (una guardia rechaza toda cifra de dinero), no pide datos y lleva a WhatsApp con el mensaje armado por el servidor o al cotizador (`/contacto/?servicio=<clave>`). Tope de gasto diario que falla cerrado: sin clave, apagado desde el panel o sin presupuesto ofrece solo WhatsApp. Guarda cada turno 90 días con teléfonos y correos tapados bajo un id de conversación de la pestaña (`api/src/asesor/guardado.ts`); "empezar de nuevo" la borra también en la API, el aviso del chat y la política de datos lo dicen, y el panel las muestra con métricas. Si la persona cotiza en la misma visita, el lead queda ligado a su conversación. El facilitador del mundo pixel (estudio y sala) también responde con este asesor: campo `home/PreguntaPixel.astro`, respuesta en su burbuja con WhatsApp, cotizador y "Seguir en el chat" (`src/lib/motion/pregunta.ts`). Panel y facilitador comparten historial, límite y gasto en `src/lib/conversacion.ts` y se avisan con un evento. Para probar en local: `cd api && npm run migraciones:local && npm run dev` y build con `PUBLIC_API_URL=http://127.0.0.1:8787` (la API en vivo no acepta `localhost`). Receta en la skill `chat-ia`; detalle en `api/README.md`.
- Suscripción a novedades: la sección de la home (`home/Novedades.astro`, con intereses por servicio), el formulario del pie (`Footer.astro`, que no se repite en la home) y la segunda casilla del cotizador solo aparecen con `PUBLIC_API_URL`. La home y el pie comparten la lógica en `src/lib/novedades.ts`. Las páginas `/novedades/` (archivo de campañas públicas y registro) y `/novedades/preferencias/` (confirmar, baja, temas, idioma y pausa; `noindex`, fuera del sitemap) tienen su versión en `/en/news/`; la API redirige a ellas y sus botones son formularios que hacen POST a la API (la CSP permite ese `form-action`). `REGALO_NOVEDADES` en `src/data/site.ts` queda en `null` hasta que el cliente entregue el regalo. El texto de autorización de novedades es distinto del de la cotización (`src/data/consentimiento.json`).

## Reglas del proyecto

- **Marca:** usa solo los tokens de `global.css` (paleta oficial de `marca/README.md`). Cian oficial `#3BC8F3`, no `#49C1EC`. `--color-deep` no sirve para texto sobre fondo oscuro. Fuentes: Cal Sans (títulos), Poppins (texto), Modulus solo como acento grande (cifras), Plex Mono para detalles de oficio.
- **Logo:** las formas vienen de `src/data/logo.ts`. El frasco del hero y el favicon son un recorte del wordmark, nunca un frasco dibujado aparte.
- **Contenido:** no inventes clientes, cifras, testimonios ni servicios. Los datos vienen del cliente (`auditoria/02-prompt-claude-design.md` §1, `marca/clientes.md`). Los testimonios actuales no se usan hasta validarlos.
- **Textos de interfaz:** sin guiones largos ni semilargos, sin emojis. Cada texto nuevo va en los dos idiomas.
- **Accesibilidad (WCAG 2.2 AA):** un solo `h1` por página, enlaces y botones reales, áreas táctiles de 44 px, `alt` descriptivo, foco visible.
- **Motion:** el HTML y el CSS pintan el estado final; nada se esconde desde el CSS esperando un observer. Si un script fija un estado inicial oculto, debe tener fail-open (un `catch` que devuelve la visibilidad) y no correr con movimiento reducido. Anima solo `transform`, `opacity` y `clip-path`. Todo bucle de más de 5 s tiene pausa y se detiene fuera de pantalla. Respeta `prefers-reduced-motion`. Tokens de duración y curvas en `global.css`.
- **Rendimiento:** presupuesto de LCP ≤ 2,5 s en móvil 4G, JS inicial ≤ 170 KB gzip, carga inicial móvil ≤ 1,5 MB. Línea base medida (30/09/2026): el JS de la home suma 70 KB gzip en 7 archivos, 48 KB de ellos el núcleo de motion (GSAP, ScrollTrigger, SplitText y Lenis en `core`). Medición del 01/10/2026, con la PWA y la suscripción: 60 KB gzip en 8 archivos más 1,4 KB en línea (el service worker no cuenta: se registra después de `load`). Medición del 02/10/2026 con la home clara y su motion (GSAP, ScrollTrigger, SplitText y Lenis): 66,9 KB gzip en 11 archivos; `/servicios/` en 66,1 KB. Medición del 05/10/2026 (hero actual, asesor y páginas nuevas; build local con `astro preview`, sin compresión del servidor, 390 px, 4G lenta de 150 ms y 1,6 Mbps, CPU 4x, mediana de 3): JS inicial de 73 KB gzip en la home y 68,6 KB en línea, oferta y solución; LCP de 1,6 s en la home, 2,1 s en `/servicios/` (el peor), 1,7 s en línea y oferta y 0,7 s en solución y contacto; carga al `load` de 740 KB en la home y 300 KB en las internas. Mide de nuevo al agregar piezas.

## Motion y verificación visual

- Para trabajo de motion usa la skill del proyecto `motion-landing` (`.claude/skills/motion-landing/`): método, recetas GSAP en `references/tecnicas.md` y verificación con capturas.
- Capturas: `node .claude/skills/motion-landing/scripts/capturar.mjs pasos.json capturas/` con el sitio levantado (`npm run build && npm run preview`). Hojas de contacto: `python3 .claude/skills/motion-landing/scripts/hoja.py`.
- Capturar sitios externos en el contenedor en la nube: Chromium no lee la CA del proxy del entorno. Agrega en `pasos.json` el campo `"angle"` con las banderas de GPU más `--ignore-certificate-errors-spki-list=<hash>`, donde el hash sale de `openssl x509 -in /root/.ccr/agent-proxy-ca.crt -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64`. ## Despliegue

- `.github/workflows/deploy.yml` sube `dist/` por FTP a `public_html` de Hostinger. Es manual (Actions > Run workflow) hasta el lanzamiento; sin los secrets `FTP_SERVER`, `FTP_USERNAME` y `FTP_PASSWORD` se omite con un aviso.
- `.github/workflows/ci.yml` corre `check`, pruebas y `build` del sitio, y `check` y pruebas de la API, en PRs y ramas.
- Vista previa: `.github/workflows/preview.yml` sube `dist/` a Cloudflare Pages (proyecto `antidoto-web`) en cada push con `wrangler`. Cada rama tiene su URL `<rama>.antidoto-web.pages.dev` y `main` publica en `antidoto-web.pages.dev`; la URL queda en el resumen del job. Necesita los secrets `CLOUDFLARE_API_TOKEN` (permiso Cloudflare Pages: Edit) y `CLOUDFLARE_ACCOUNT_ID`; sin ellos se omite con un aviso. `public/_headers` pone `noindex` a las URLs `*.pages.dev`.
- API: `.github/workflows/api.yml` despliega `api/` en cada push a `main` que la toque, o a mano. Crea la base D1 si no existe, aplica migraciones y copia los secrets `RESEND_API_KEY`, `SAL_IP` y `RESEND_WEBHOOK_SECRET` al Worker. El token de Cloudflare necesita además *Workers Scripts: Edit* y *D1: Edit*. La variable de GitHub `PUBLIC_API_URL` conecta el sitio con la API (preview y deploy la pasan al build).
- `public/.htaccess` trae redirecciones HTTPS y sin www, 404 real, cabeceras de seguridad (CSP en Report-Only) y caché.
